# Deployment guide (Render + Hostinger domain)

The whole app runs as **one container**: the Express API, SQLite database, cron
scheduler, and the built React editor. No separate frontend host is needed.

## Prerequisites

- Your domain registered at Hostinger: `layerup.host`
- A GitHub account (Render/Railway deploy from a Git repo)
- A Render or Railway account (free tier is enough to start)

## 1. Push the project to GitHub

From `D:\Open Code\n8n-from-scratch`:

```powershell
git init
git add .
git commit -m "n8n from scratch: engine, API, editor, credentials"
git branch -M main
git remote add origin https://github.com/<YOUR_USERNAME>/<YOUR_REPO>.git
git push -u origin main
```

`.gitignore` already excludes `node_modules`, `dist`, and `data/`, so the
SQLite database and local encryption key will not be uploaded.

## 2. Deploy on Render

1. Go to https://dashboard.render.com → **New → Web Service**.
2. Connect the GitHub repository. Render reads `render.yaml` automatically and
   configures a Docker service using the `Dockerfile`.
3. Service settings:
   - **Build command**: handled by the Dockerfile
   - **Start command**: handled by the Dockerfile (`node dist/src/server/index.js`)
   - **Health check path**: `/health`
4. Environment variables (already in `render.yaml`):
   - `ENCRYPTION_KEY` — generated by Render; **save this value somewhere safe**.
   - `API_KEY` — a long random token; all `/api` calls require
     `Authorization: Bearer <API_KEY>`. In the editor, click **API key** and paste
     the same value. `/health` and the webhooks remain public (webhooks use their
     own per-workflow token).
   - `DB_PATH=/app/data/workflows.db`
   - `KEY_PATH=/app/data/.encryption-key`
   - `PORT=3000`
   - `DATABASE_URL` — provided by the `n8n-db` Postgres service in `render.yaml`.
     When set, workflows, credentials and execution history persist in Postgres
     instead of the ephemeral SQLite file.
5. Deploy, then open `https://<YOUR_SERVICE>.onrender.com/health` — you should see
   `{"status":"ok",...}`. The root URL should show the workflow editor.

### Railway alternative

1. https://railway.app → **New Project → Deploy from GitHub repo**.
2. Railway detects the `Dockerfile` automatically.
3. Set the same environment variables in the service's **Variables** tab.
4. Open **Settings → Networking → Generate Domain** to get a public URL.

## 3. Point your Hostinger domain at the app

In Render: **Settings → Custom Domains → Add Custom Domain**, enter both:

- `layerup.host`
- `www.layerup.host`

Render will show the exact DNS records it needs. In Hostinger:

> Current state of `layerup.host`: the apex has an `A` record to `2.57.91.91`
> (Hostinger's parked-domain page) and `www` is a `CNAME` to the apex. Replace
> these records — the parking page will disappear once the new records resolve.

1. Open **hPanel → Domains → DNS / DNS Zone Editor** for `layerup.host`.
2. Add the records Render shows, typically:
   - `www` → `CNAME` → `<YOUR_SERVICE>.onrender.com`
   - `@` (apex) → `A` record to Render's displayed IP, or a `CNAME` if Render
     offers CNAME flattening for the apex.
   **Exact records for this deployment** (Render service: `n8n-from-scratch`):
   - `www` → `CNAME` → `n8n-from-scratch.onrender.com`
   - `@` (apex) → `A` → `216.24.57.1`
     (or `CNAME` → `n8n-from-scratch.onrender.com` if Hostinger allows a root CNAME)
3. Save. DNS propagation can take a few minutes to a few hours.
4. Render provisions a free TLS certificate automatically. Once it is active,
   `https://layerup.host` will serve the editor.

For Railway, the same idea: **Settings → Domains → Custom Domain**, then add
the CNAME record shown by Railway in Hostinger's DNS editor.

## 4. Verify

```powershell
curl.exe https://layerup.host/health
curl.exe https://layerup.host/api/nodes
```

Open `https://layerup.host` in a browser — you should see the workflow editor with
the node palette and workflow dropdown.

## Data persistence

The app picks its store automatically:

- **`DATABASE_URL` set** → Postgres. Workflows, credentials and execution history
  survive redeploys. `render.yaml` creates a `n8n-db` Postgres service and wires
  its connection string into the web service.
- **No `DATABASE_URL`** → SQLite at `DB_PATH` (default `data/workflows.db`).
  Zero setup, but Render/Railway free tiers have an **ephemeral filesystem**, so
  the file is wiped on restart or redeploy.

Always keep `ENCRYPTION_KEY` set as an environment variable so encrypted
credentials remain decryptable if the database is ever reset.

## Postgres expiry plan (important)

Render's free Postgres plan expires **30 days after creation** — for this
deployment, around **24 December 2026**. Pick one of these before then:

**Option A — keep Render (simplest):** upgrade `n8n-db` to a paid plan in the
Render dashboard. `DATABASE_URL` stays the same and no code or redeploy is
needed.

**Option B — move to another provider:** create a Postgres database on Railway,
Supabase or Neon, then:

1. Take a backup from the current database:
   ```powershell
   $env:DATABASE_URL = "<current external database URL>"
   npm run db:backup
   ```
2. Point `DATABASE_URL` at the new database in Render's **Environment** tab and
   save (this triggers a redeploy).
3. Restore the backup into the new database:
   ```powershell
   $env:DATABASE_URL = "<new database URL>"
   npm run db:restore -- backups\workflows-<timestamp>.json
   ```
4. Keep `ENCRYPTION_KEY` unchanged — credential secrets are encrypted with it.

`npm run db:backup` exports workflows, encrypted credentials and up to 500
executions to `backups/*.json` (gitignored). Run it periodically even before a
migration. Workflow and credential IDs are preserved on restore; execution IDs
are regenerated.

On Railway, create a Postgres service, add its `DATABASE_URL` variable to the
web service, and redeploy.

## Local production-style test

```powershell
npm run build
cd ui && npm run build && cd ..
npm start        # serves API + UI on http://localhost:3000
```

The compiled server serves the UI at `/`, the API under `/api`, webhooks under
`/webhook`, and falls back to the SPA for client-side routes.
